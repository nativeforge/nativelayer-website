# WebAssembly GC: Writing Real Apps in Wasm Without C

WebAssembly started as a compilation target for C and C++ code. WebAssembly GC (Garbage Collection) changes that entirely: it lets languages like Kotlin, Dart, and OCaml compile to Wasm without bundling their own garbage collector, producing dramatically smaller and faster binaries.

## What Wasm GC Actually Is

Before Wasm GC, languages with managed memory (GC languages) had two options:
1. Compile the entire runtime + GC into the Wasm binary (Blazor ships a 5MB runtime)
2. Manage memory manually in C/Rust (not practical for most languages)

Wasm GC adds first-class heap objects, references, and GC integration directly into the Wasm spec. The browser's existing GC handles memory: the language just needs to compile to Wasm GC instructions.

## Kotlin/Wasm

Kotlin is leading the charge. With `kotlin-wasm` target:

```kotlin
@JsExport
fun greet(name: String): String {
  return "Hello, $name! This runs in Wasm."
}
```

Compiled output: ~150KB (vs. ~2MB for Kotlin/JS). The binary integrates with JavaScript via the Wasm component model, passing strings and objects through a well-defined ABI.

Kotlin Compose for Web now targets Wasm: full component UIs running as Wasm, no transpilation.

## Dart + Flutter Web

Flutter Web's default mode already uses Wasm GC in Chrome. Apps compile from Dart → Wasm GC with virtually no size penalty from the runtime. Performance is significantly closer to native Flutter than the previous JS-compiled output.

```dart
import 'dart:js_interop';

@JS('window.customAlert')
external void customAlert(String message);

void main() {
  customAlert('Hello from Dart Wasm!');
}
```

## The Component Model

The Wasm Component Model standardizes how Wasm modules export and import typed interfaces. Instead of raw bytes, you get:

```wit
// Component interface definition language
interface blog-api {
  record post {
    id: string,
    title: string,
    content: string,
  }
  get-post: func(id: string) -> option<post>
  list-posts: func() -> list<post>
}
```

This enables polyglot composition: a Rust module and a Kotlin module can share types without manual marshaling.

## Browser Support

Wasm GC shipped in Chrome 119, Firefox 120, and Safari 18. It's now baseline. This means Kotlin/Wasm and Flutter Web are production-viable today.

## What This Changes

The practical implication: teams working in strongly-typed, GC languages (Kotlin, Dart, Swift, OCaml) can now target the browser without JavaScript or TypeScript. The web becomes a genuinely polyglot platform.

For JavaScript developers, Wasm GC creates competition at the performance layer. Compute-heavy UI components written in Kotlin/Wasm will routinely outperform equivalent JS, especially on lower-end devices.
